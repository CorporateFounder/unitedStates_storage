## 2. Current burn address placeholder

Both wallet and server still define:

- `V35_RESCUE_FORK_INDEX = Long.MAX_VALUE`
- `V35_BURN_ADDRESS = "TODO_V35_BURN_ADDRESS"`

The final burn address has not been set. V35 remains disabled.

`BurnAddressPolicy` exists in both projects, but it is still a helper only. It is not wired into block validation, balance accounting, transaction pool admission, or controller transaction submission.

## 3. Address and signature format findings

Current address format is effectively a Base58-encoded compressed secp256k1 public key:

- `UtilsSecurity.generateKeyPair()` creates a secp256k1 keypair.
- It compresses the public key with `UtilsSecurity.compressed(...)`.
- It encodes that compressed public key using `Base58`.
- Existing normal account addresses, including founder and BASIS, use this format.

`DtoTransaction.verify()` verifies the sender only:

1. Base58-decodes `sender`.
2. Decodes the bytes as a secp256k1 public key via `UtilsSecurity.decodeKey(...)`.
3. Rebuilds the signed payload from `sender + customer + digitalDollar + digitalStockBalance + laws + bonusForMiner`.
4. Verifies the signature with the decoded sender public key.

Important finding: `DtoTransaction.verify()` decodes the sender before it checks for blank values or returns false. Therefore an invalid or non-public-key sender string can throw or fail before normal false-return validation.

Recipient/customer address validation is looser:

- The recipient is part of the signed payload.
- The recipient does not need to sign.
- `UtilsBalance.sendMoney(...)` blocks sending to `BASIS_ADDRESS`, but it does not otherwise require recipient public-key decoding.
- `UtilsUse.balanceTransaction(...)` creates a zero-balance account for a missing recipient.

Therefore normal transfers can send to an arbitrary non-BASIS recipient string at the accounting layer, but sender-side validation requires the sender to be a decodable public key unless consensus rejects it earlier.

## 4. Recommended final burn address model

Recommended model: use a syntactically valid CITU address generated by the existing key/address format, then make it permanently unspendable by operational procedure and V35 consensus policy.

Recommended operational procedure:

1. Generate a fresh CITU keypair offline using the same address format as normal accounts.
2. Publish the generated public address as the final `V35_BURN_ADDRESS`.
3. Destroy the private key and document the ceremony/process.
4. Do not use the address for anything except receiving burned GOLD.
5. Add V35 consensus no-spend enforcement so that even if a private key is later claimed, spending from the burn address is invalid after V35.

This model is safer for the current codebase than a random invalid sentinel string because existing sender verification expects Base58 public-key sender strings.

Alternative model: use a sentinel/impossible address such as `CITU_V35_BURN_...`.

- Advantage: easier to communicate as intentionally unspendable.
- Risk: if it ever appears as `sender`, current `DtoTransaction.verify()` may attempt Base58/public-key decoding and can fail before a clean validation false.
- Requirement if chosen: validation and transaction-pool code must reject burn-address sender before any call to `DtoTransaction.verify()`.

Recommendation: use a syntactically valid generated address plus explicit no-spend enforcement.

## 5. Whether burn address can be unspendable

Yes, but with a layered definition:

- Operationally unspendable: generated offline and private key destroyed/not retained.
- Consensus unspendable: after V35, any transaction whose sender equals `V35_BURN_ADDRESS` is invalid.

The codebase cannot prove that a syntactically valid public-key address has no private key. Consensus no-spend enforcement is therefore required for final trust.

If a syntactically invalid sentinel address is used, it can be unspendable by construction, but only if all sender-spend attempts are rejected before signature decoding.

## 6. Whether normal signed burn transaction can send to it

Yes, if the burn address is a non-BASIS recipient.

The intended founder burn transaction:

- sender: `Seting.ADDRESS_FOUNDER`
- customer: final `Seting.V35_BURN_ADDRESS`
- GOLD: burn amount
- stock/silver: `0.00`
- signature: founder private key signs the existing `DtoTransaction.toSign()` payload

This should work as a normal transaction because:

- `DtoTransaction.verify()` validates the founder sender signature.
- The recipient does not need to sign.
- `UtilsBalance.sendMoney(...)` allows non-BASIS senders to non-BASIS recipients.
- `UtilsUse.balanceTransaction(...)` can create the recipient account if it does not already exist.

No transaction format or block format change is needed.

## 7. Recommended no-spend enforcement rule

Recommended rule:

After V35, any transaction with `sender == BurnAddressPolicy.getBurnAddress()` is invalid.

Strict activation gate:

- Apply only when `Seting.V35_RESCUE_FORK_INDEX != Long.MAX_VALUE`
- Apply only for block/transaction index `>= Seting.V35_RESCUE_FORK_INDEX`
- Before V35, preserve legacy validation unless Phase 5B explicitly chooses a stricter pre-V35 policy.

Recommended placement:

1. In `UtilsBlock.validationOneBlock(...)` and `UtilsBlock.validationOneBlockWithCanonicalContext(...)`, check burn-address sender before `transaction.verify()` is called.
2. In `UtilsUse.balanceTransaction(...)`, reject burn-address sender after V35 before balance mutation.
3. In `UtilsBalance.calculateBalance(...)`, keep a matching guard or rely on block validation only if all balance paths are proven to validate first.
4. In server transaction-pool admission (`AllTransactions`), reject burn-address sender after V35 before `dtoTransaction.verify()`.
5. In wallet transaction creation/submission paths, prevent users from creating/sending a burn-address sender transaction after V35.

The validation path must return false/reject cleanly and must not throw for malformed burn-address sender data.

## 8. Whether spending from burn address before V35 should be blocked

Recommended Phase 5B-1 policy: preserve legacy behavior before V35.

Reason:

- The user requirement says V35 behavior begins after V35.
- V35 remains disabled.
- Pre-V35 chains must not be reinterpreted.

Operationally, if the real burn transaction is executed before V35, the burn can still be considered final if:

- the final address is operationally unspendable, and
- V35 later locks spending from it forever.

Optional stricter policy: block burn-address spending immediately at the next planned release even before V35. This would be safer for the public burn but would be a behavior change before V35 and should be a separate explicitly approved phase.

## 9. Whether burn address should be hardcoded in Seting.java

Yes. The final burn address should be a consensus constant in `Seting.java` for both wallet and server.

Reasons:

- All nodes must agree on the exact burn address.
- `BurnAddressPolicy` currently reads from `Seting.V35_BURN_ADDRESS`.
- Keeping the address in `Seting` matches the existing pattern for `ADDRESS_FOUNDER`, `BASIS_ADDRESS`, and V35 constants.

`BurnAddressPolicy` should be the only helper API used by validation code, but `Seting.V35_BURN_ADDRESS` should remain the source constant.

Recommended structure:

- `Seting.V35_BURN_ADDRESS` = source-of-truth constant value.
- `BurnAddressPolicy` = source-of-truth behavior: `isBurnAddress`, `canSpendFromAddress`, and safe validation helpers.
- Production validation should call `BurnAddressPolicy`, not duplicate string comparisons.

## 10. Whether consensus changes are needed

Yes, for no-spend enforcement.

The founder burn itself can be a normal signed transaction and does not need consensus changes. But the claim that burned coins are permanently unspendable requires consensus enforcement after V35.

Required consensus change:

- reject any transaction spending from `V35_BURN_ADDRESS` after V35.

Non-consensus but strongly recommended:

- supply accounting helpers to report burned/outstanding/circulating supply correctly.
- API/dashboard updates in a later phase.

## 11. Exact safe implementation order for Phase 5B-1

Recommended order:

1. Choose the final burn address model.
2. If using the recommended generated-address model, generate the final address offline and publish it.
3. Replace `TODO_V35_BURN_ADDRESS` in both wallet and server `Seting.java`.
4. Extend `BurnAddressPolicy` with any missing safe helper methods, for example `isNoSpendActive(index)` and `isSpendForbidden(index, sender)`.
5. Add tests proving V35 remains disabled and the burn address is no longer the TODO placeholder.
6. Add tests proving normal founder-to-burn recipient behavior can be represented without changing `DtoTransaction`.
7. Add validation no-spend guard before `DtoTransaction.verify()` in block validation.
8. Add transaction-pool/admission no-spend guard where transactions are accepted before block validation.
9. Add balance/accounting safety tests so burn-address sender does not mutate balances after V35.
10. Confirm legacy pre-V35 behavior remains unchanged while V35 is disabled.

## 14. Required tests

Required design/constant tests:

- `V35_RESCUE_FORK_INDEX == Long.MAX_VALUE` in wallet and server.
- `V35_BURN_ADDRESS` is not `TODO_V35_BURN_ADDRESS` after Phase 5B-1.
- wallet/server burn constants match.
- `BurnAddressPolicy.isBurnAddress(finalAddress)` returns true.
- `BurnAddressPolicy.canSpendFromAddress(preV35, burnAddress)` preserves chosen legacy policy.
- `BurnAddressPolicy.canSpendFromAddress(v35Index, burnAddress)` returns false when a simulated active fork index is used.

Required transaction tests:

- founder-to-burn transaction can be represented as a normal `DtoTransaction`.
- burn address as recipient does not require recipient signature.
- burn address as recipient is not treated as `BASIS_ADDRESS`.
- normal non-burn senders still validate after V35.

Required no-spend tests:

- burn-address sender after V35 is rejected before signature decode.
- malformed/signature-invalid burn-address sender after V35 does not crash.
- huge or fake burn-address spend does not mutate balances.
- server transaction-pool admission rejects burn-address sender after V35.
- old pre-V35 behavior remains unchanged while V35 is disabled.

Required parity tests:

- wallet/server `BurnAddressPolicy` behavior matches.
- wallet/server validation behavior matches.

## 15. Risks

Highest risks:

1. The burn address is still a TODO placeholder.
2. A valid generated address cannot mathematically prove private-key destruction; public trust needs both ceremony and consensus no-spend enforcement.
3. A sentinel invalid address can crash or fail unpredictably if used as sender unless every path rejects before `DtoTransaction.verify()`.
4. Current validation calls `transaction.verify()` inside block validation before any burn-address sender guard exists.
5. Transaction-pool admission also calls `dtoTransaction.verify()` before any burn-address no-spend policy.
6. If pre-V35 burn-address spending remains legacy, a burn done before V35 depends on operational unspendability until the fork activates.
7. Changing `DtoTransaction.verify()` directly would be high risk because it affects all signature validation.

## 16. Rollback plan

Before the real burn transaction is broadcast:

- Revert `Seting.V35_BURN_ADDRESS` to placeholder or choose a different final address.
- Revert no-spend wiring while V35 remains disabled.
- Rerun wallet/server tests.

After the real burn transaction is confirmed:

- Do not rollback by spending from the burn address; that would destroy public trust in the burn.
- If the final address or no-spend rule is wrong, disclose immediately and use a narrowly scoped hard fork only if absolutely necessary.

After V35 activation:

- If no-spend enforcement rejects valid legacy blocks, use emergency patch/fork procedures.
- If no-spend enforcement is too weak, patch all validation and transaction admission paths before further activation milestones.

## 17. Recommendation

Use a syntactically valid generated CITU address as the final burn address, publish it as a consensus constant in `Seting.V35_BURN_ADDRESS`, and route all no-spend behavior through `BurnAddressPolicy`.

Do not use the TODO placeholder. Do not use a random invalid string unless Phase 5B-1 first adds pre-verify guards in every sender-validation and transaction-admission path.

Recommended next phase:

Phase 5B-1 - set the final burn address and wire burn-address no-spend enforcement behind the V35 fork gate, with V35 still disabled.
